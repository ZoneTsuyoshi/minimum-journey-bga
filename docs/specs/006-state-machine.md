## 目的

BGA のゲームはサーバー側の状態機械で進行する。この仕様書は、MINIMUM JOURNEY の各状態について「誰がアクティブか」「どのアクションを受け付けるか」「クライアントへ何を渡すか」「どこへ遷移するか」を定義する。後続のデータモデル・通知（T-007）、カード効果（T-008）、実装は、この仕様書の状態 ID・状態クラス名・アクション名を土台にする。

## スコープ

- 対象: 状態の一覧と遷移、準備フェイズの同時選択と「全員が選ぶまで変更可能」の実現方法、ドロー時効果の解決の状態設計、探査フェイズ・帰還フェイズの状態設計、zombie の既定行動、ゲーム進行度の式、状態ごとの非公開情報の方針、テスト観点
- 対象外: ルールそのもの（001・010・011 が正）、カード効果の内部実装（T-008）、DB スキーマ・通知の詳細一覧（T-007）、画面の見た目（009 / T-009）。擬似コードは示すが実コードは書かない

## 記法

- **【確認】** は BGA 公式ドキュメント（`https://en.doc.boardgamearena.com/` 配下）で確認した事実。URL を添える。ページは WebFetch（本文を要約して返すツール）で取得した要約を介した確認で、メソッドの細かい挙動は Studio での実機確認を前提とする。
- **【提案】** は本仕様書の設計案。公式ドキュメントでは確認していない。
- **【未確認】** は確認を試みたが公式ドキュメントから判断できなかった事項（「未確定事項 A」に集約）。
- ルールの根拠は `001 §N`、`010 §N（D2 などの作者回答番号）`、`002 No.N` の形式で示す。
- 「P0〜P6、P2a、6b」は 010 の優先度と手順番号。

### 2. 状態の一覧

状態 ID は 10 刻みのブロックで割り当てる（1・99 は予約のため避ける。B2）。状態は **26 個**（GAME 13、ACTIVE_PLAYER 10、MULTIPLE_ACTIVE_PLAYER 3）。private parallel states は採用しない（§5.3）。

**共通の約束**

- クラス名は `Bga\Games\minimumjourney\States\<クラス名>`（名前空間の大文字小文字は 003 の U1 に従う）。
- 全ての GAME 以外の状態に `zombie()` を実装する（§7）。
- 「args」の【公開】は全員、【本人】は `_private[プレイヤー ID]`。
- 遷移は戻り値（遷移名）で書く。表の「→」は `transitions` に登録する遷移名と先の状態。
- 永続データ（`prep_choice`、`resolve_level` など）の保存先・名前は T-007 で決める。この表では論理名で書く。

#### 4.2 実現方法の比較

| 案 | 方式 | 長所 | 短所 |
| --- | --- | --- | --- |
| A | 全員が `MULTIPLE_ACTIVE_PLAYER` でアクティブのまま。選択を DB に保存するだけで `setPlayerNonMultiactive` は呼ばない。全員の選択が埋まった時点で、サーバーが `setAllPlayersNonMultiactive('allChosen')` を呼ぶ | 選択後の変更が通常のアクションで済み、フレームワークの追加機能に依存しない。「選択済み」はアクティブ一覧とは無関係に自前で管理でき、確定の瞬間も自前で決められる | 選び終えた人も全員が確定するまでアクティブ扱い。BGA の持ち時間が選び終えた人にも減る可能性が高い（U2）。BGA 標準の「待機中」表示と食い違い、チェックマークは自前の表示になる。早く選んだ人の持ち時間が不利になる |

#### 4.3 推奨【提案】: 案 B（フォールバックは案 A）

推奨は **案 B** とする。理由は、(1) 持ち時間が選び終えた人に減らない（U2 の懸念を避けられる）、(2) 「選択済みかどうか」を BGA 標準の待機表示で表せて 009 §9.1 の「チェックマークだけ見せる」と一致する、(3) 最後の 1 人の選択が確定のトリガーなので、009 のエッジケース（直前の変更との競合）をサーバー側の状態チェックだけで順序付けできる、の 3 点。案 C は競合が複雑なので採用しない。

**案 B の動作**

```text
onEnteringState (PrepChoice):
    needChoice = PrepStepStart が決めた「要選択」のプレイヤー集合   # 後選び・確定済みは含めない
    setPlayersMultiactive(needChoice, 'allChosen', bExclusive = true)

actSelectPrep(choice):           # #[CheckAction(false)] で自前検証
    state が PrepChoice であり、playerId が needChoice に含まれることを検証
    choice == 'draw' なら 山札が 1 枚以上であることを検証（R4）
    first = (prep_choice[playerId] is null)
    prep_choice[playerId] = choice                 # 上書き可
    通知: 本人にだけ「選択を記録」（_private）。公開通知には内容を載せない
    if first:
        setPlayerNonMultiactive(playerId, 'allChosen')   # 最後の 1 人なら自動遷移
    # 2 回目以降（変更）は何もせず、アクティブ状態も変えない
```

- 変更の可否はサーバーが「現在の状態が `PrepChoice` で、自分が選択者で、`prep_choice` が既にある」ことで判定する。確定（`allChosen` 遷移）後は状態が変わるので、変更アクションはフレームワーク側で拒否される（U1）。
- クライアントは `allChosen` 後の公開通知（開示）を受けたら、[Draw]/[Stop]/[Change] を無効にする（009 §9.1）。
- 公開される情報は `chosen`（選び終えた人の ID）だけ。args の公開部分には選択内容を絶対に入れない（B5、B11）。`myChoice` は `_private` で本人にだけ返す。再読み込み（F5）後も `getArgs` が `_private.myChoice` を返すので、選択済み表示と [Change] 操作が復元できる。

**案 A に切り替える条件**: Studio での検証（テスト観点 T1）で、非アクティブな選択済みプレイヤーの `actSelectPrep` が受け付けられない、または確定後の変更要求が不整合を起こす場合。案 A では `PrepChoice` で `setAllPlayersMultiactive` の代わりに `setPlayersMultiactive` で要選択者全員をアクティブにし、`prep_choice` が全員分埋まった時点で `setAllPlayersNonMultiactive('allChosen')` を呼ぶ。「選択済み」の公開は通知（内容なし）で行う。

#### 4.4 最後の 1 人の選択と直前の変更の競合

| 状況 | 結果 |
| --- | --- |
| 最後の 1 人の `actSelectPrep` が先に処理された | 全員の選択が確定し 22 `PrepLock` へ遷移。後から届いた変更要求は状態不一致で拒否される。拒否された人の画面は、開示通知で確定した選択に更新される。エラー表示は「The choices are already locked」程度の穏当な文言にする（009 §9.1 は「エラーにせず無視」だが、フレームワークが状態不一致を例外にする場合は文言で穏当にする。U1） |
| 変更要求が先に処理された | 変更後の選択が有効。その後に最後の 1 人が選ぶ |
| 同時に届いた | サーバーが処理した順（U3）。どちらが先でも不整合は起きない（選択は上書き、確定は「全員の選択が埋まった」ときに 1 回だけ） |

確定の判定は `setPlayerNonMultiactive` の「最後の 1 人」ではなく、常に永続データ（`prep_choice`）を正とする。通知の到着順や画面の表示は判定に使わない。

#### 4.5 049 の後選び

- 049 の持ち主（記録は P6 で作られ、次の `PrepStepStart` で読む）は、`PrepChoice` に参加しない。他の要選択者が全員選び終えて 22 `PrepLock` に入った時点で、**他プレイヤーの選択を公開**する（D9「他プレイヤーの開示後に選べます」）。続いて 23 `PrepChoiceLate` で 049 の持ち主が選び、押した時点で確定（009 §9.1）。
- 他プレイヤーの選択は 22 で確定し、049 の持ち主の選択を見て変更することはできない（暫定。「全員が選び終わるまで変更可能」の「全員」に 049 の持ち主を含めるかは未確定事項 No.1）。
- 054 の強制ドローがあるときは 049 の持ち主もドロー固定（H3）。`PrepStepStart` がドロー確定にするので 23 には入らない。
- 049 の持ち主の山札が 0 枚なら、ストップ確定（選べない）で 23 には入らない。
- 049 の持ち主が 028・029 の影響を同時に受けることはない（引いたカードは 1 枚。H7）。

#### 4.7 開示後の処理（24 `PrepReveal`）と山札 0 枚・準備終了

- ドロー人数の判定は、054 による強制ドローを含め、実際に山札から引けた人数で行う（001 §5 ③-3、D12）。山札 0 枚でドローできない人はストップ扱い。
- 「準備終了」（`prep_finished`）は、ストップを選んだ（または山札 0 枚でストップ確定になった）プレイヤーに、開示時点で立てる【提案】。024 の P3 が「既に準備終了しているプレイヤー」に、その回にストップしたプレイヤーを含めるかは未確定（未確定事項 No.2）。
- ストップした人が引く裏向きカードは、ドロー 1 人以上の回に限り、山札の上から実際に取り出して「裏向きの別置き場」に移す（001 §5 ②-3、Q-32）。同じプレイヤーが 054 の打ち消しの後に再びストップすると別置き場に 2 枚以上になりうる。打ち消されたプレイヤーの既存の裏向きカードの扱いは 001 Q-34（未回答）。状態機械は別置き場を枚数の制限なしの集合として扱い、扱いが決まるまで**そのまま残す**。
- 054 のカードが 043 で山札に戻された場合は強制ドローの記録を作らない（H2）。その回の最終確定（P6 の最後）まで記録は仮扱い（§5.2）。

#### 5.2 解決エンジン（30 `DrawResolve`）の設計【提案】

010 §6.1 の手順を、永続カーソル `resolve_level` と解決キューで状態に落とす。キューは「引かれたカード」と「046 の付加カード」を要素とし、各要素は `owner`・`cardId`・`level`・`status`（`pending` / `valid` / `invalid` / `returned` / `done`）・`copySource`（008 のみ）を持つ。

```text
state DrawResolve.onEnteringState():
    loop:
        switch resolve_level:
            case INIT:          # 010 §6.1 手順 3: キュー構築。ドロー時効果を持たないカードは対象外
                resolve_level = P0
            case P0:            # 手順 4: 054 の仮記録（039・053 の影響を受けない。D2）
                recordForceDraw(queue.filter(054)); resolve_level = P1
            case P1:            # 手順 5: 抑止の判定。結果は status に書き、公開通知
                applyFilters(queue); resolve_level = P2
            case P2:            # 手順 6: 043
                if existsValid(043) and targets nonempty:
                    resolve_level = P2_WAIT; return 'pod'        # → 31。戻ってきたら P2_WAIT で結果を適用
                resolve_level = P2A
            case P2_WAIT:       # 31 の決定を適用: 戻したカードを山札へ → シャッフル → 1 枚準備（効果は発動しない。D7）
                applyReturns(); 戻された 054 の仮記録を取り消す（H2）; resolve_level = P2A
            case P2A:           # 手順 6a: 046
                for 046 in queue where valid: attach top card
                    付加カードが 039/053（P1 相当）: そのフィルタを「未解決の効果」にだけ適用（J2）
                    付加カードが 043（P2 相当）: P2 を再実行（31 を再入場。J2: 決着済みには遡らない）
                    付加カードが 054（P0 相当）: 解決位置が未確定（010 Q-22）→ 暫定: その場で P0 の記録だけ行う
                    付加カードが P3〜P6 相当: キューに本来のレベルで追加（J1）
                resolve_level = COPY
            case COPY:          # 手順 6b: 008 のコピー元（K1）
                for 008 in queue where valid and not returned (付加カードの 008 を含む):
                    if candidates nonempty: resolve_level = COPY_WAIT; return 'copy'   # → 32
                resolve_level = P3
            case COPY_WAIT:     # 選んだカードのレベルを 008 の level に設定（H5）。次の 008 があれば COPY に戻る
                resolve_level = COPY
            case P3:            # 手順 7: 024。準備終了済みのプレイヤー（強制ドローの回は空。N38）が山札の上から 1 枚準備（効果は発動しない）
                resolve P3 entries; resolve_level = P4
            case P4:            # 手順 8: 036
                if existsValid(036): resolve_level = P4_WAIT; return 'wormhole'        # → 33
                resolve_level = P5_SEQ
            case P4_WAIT:       # 33 の結果（入れ替え・シャッフル）を適用
                resolve_level = P5_SEQ
            case P5_SEQ:        # 手順 9: 007（または 007 をコピーした 008）。D4 の順に 1 人ずつ
                if next owner exists: return 'laser'                                   # → 34（戻るたびに次の 1 人）
                resolve_level = P5_SIM
            case P5_SIM:        # 手順 9: 選択付きの効果を持つ全員を同時に
                resolve automatic parts; if anyone needs choice: resolve_level = P6; return 'simul'   # → 35
                resolve_level = P6
            case P6:            # 手順 10: 028・029・049 の記録（有効なものだけ）。054 の記録は P2 で戻されなかった場合のみ確定（H2）
                finalizeNextChoiceRecords(); 通知; return 'done'                       # → 20
```

- 「状態に入る前に自動で解決できるか」は `DrawResolve` が判定する。対象が 0 人のレベルは、状態を出ずに次のレベルへ進む（無駄な状態遷移を作らない）。
- 31〜35 の各状態の `onEnteringState` では、DB を変更するのは `getArgs` の外の副作用として扱い（B5）、`getArgs` は読み取りのみにする。
- **同優先度の順番処理（D4）**: 順番に処理する効果が複数あるレベルに備え、`DrawResolve` は「お守り所持者からの時計回り距離の大きい順」に所有者を並べ、1 人ずつ割り込み状態へ送る。探査手番決定の関数（所持者が最優先）と逆向きなので、関数を共用しない（010 §8-3）。現行カードでは 1 レベルに 1 人だけ。
- **付加カード・コピーの扱い**: 046 の付加カードは、P1・P2 相当の効果を持てば他プレイヤーの P3 以降に先立って処理される（H6）。上の擬似コードは 010 §6.2 と同じ位置に置いた。

#### 5.3 状態の割り当て方の比較と推奨

| 案 | 方式 | 長所 | 短所 |
| --- | --- | --- | --- |
| X | 効果ごとの状態の連鎖（ACTIVE_PLAYER／MULTIPLE_ACTIVE_PLAYER を 1 効果 1 状態で順に） | 状態が単純で、効果 1 つが 1 クラスに対応する。T-008 の見通しがよい | **P5-同時を全員同時に解決できない**。005・009・010・014・020・035・050・052 は別の効果で、同時（D5）に解決するには 1 つの状態に複数の効果を同時に載せる必要がある。連鎖にすると効果の数だけ順番待ちが生じ、D5 の「全員同時」に反する。状態数も増える（P5-同時だけで 8 状態） |
| Y | **ドロー時効果を「レベルごとの状態」に集約**し、P5-同時は 1 つの `MULTIPLE_ACTIVE_PLAYER` 状態に全員を載せる。効果の種類はプレイヤーごとの `_private` args で区別し、アクションは効果の種類ごとに用意する（採用案） | 同時解決が 1 状態で済み、状態数が少ない（解決用の割り込み状態は 5 つ）。1 人 1 効果なので追加の状態遷移が要らない。動的に変わる効果の数に対応できる（008 のコピー、046 の付加で効果の持ち主が変わる） | 1 つの状態クラスに複数の効果が混ざる。ステータスバーの文言は効果ごとに JS が切り替える必要がある。アクションの種類が多い（5 つ） |
| Z | private parallel states（マスター = `MULTIPLE_ACTIVE_PLAYER`、効果ごとに PRIVATE 状態） | BGA の標準機構で、1 人ずつ別々の状態を進められる。状態ごとに説明文を持てる | 全ての効果が「1 回の決定」で終わるので、複数ステップ用の機構が不要。private 状態への振り分け（`nextPrivateState` で効果別の状態へ飛ばす）が確認できていない（U4）。private 状態は ACTIVE_PLAYER にできず、離脱・再接続時の挙動が複雑。状態数が増える（効果の種類 6 つ分） |

**推奨【提案】: 案 Y**。ドロー時効果の選択は全て「1 回の決定」で完結する（確認した 12 枚で複数ステップのものはない）ため、private parallel states の利点（1 人が複数の状態を順に進む）が不要。割り込み状態を「レベル」単位にし、P5-同時だけを MULTIPLE_ACTIVE_PLAYER にまとめる。

- 前提が崩れる条件: 将来、同時に解決する効果の中に複数ステップのものが加わった場合は、`SimultaneousEffects` のうち該当する効果だけ private parallel states に移す（案 Z）。マスター状態の構造（`DrawResolve` からの 1 回の入場・全員終了で戻る）は変えなくてよい。
- 案 Y の `SimultaneousEffects` の実装方針: `onEnteringState` で、選択が要るプレイヤーだけ `setPlayersMultiactive`。`actXxx` は、そのプレイヤーの `pending effect` と一致するアクションだけを受け付け、実行後に `setPlayerNonMultiactive($id, 'allDone')`。

### 6. 探査フェイズ・帰還フェイズの状態設計

#### 6.1 探査手番のループ

```text
40 ExploreStart:
    for p in players: output[p] = computeExplorationOutput(p, round)      # 011 §6-1。以後再計算しない（A2）
    explore_order = sort(players, (準備枚数, output, 所持者からの時計回り距離))   # 001 §6-2。探査フェイズ中は固定（Q-13）
    explore_index = 0

41 ExploreTurnStart:
    if explore_index == len(explore_order): return 'allDone'               # → 50
    p = explore_order[explore_index]; changeActivePlayer(p)
    explore_state[p] = { sumCost: 0, explored: 0, usedOnExplore: {}, additionalDone: false }
    if usableOnExploreEffects(p) nonempty: return 'onExplore'              # → 42
    return 'choose'                                                         # → 43

43 ExploreChoose.onEnteringState(p):
    targets = ExploreRules.targets(p)           # 実効コスト ≤ output。006/015/021/027/037/038/047 の補正、025/026 の禁止、007 のロック（他者）を反映
    if targets is empty: log("auto pass"); return 'passed'                  # 自動パス（009 §9.2、No.8 / No.17）
    # actExplore / actPass で遷移
```

- 「探査できるカード」の判定は**サーバー**が行い、選択可能な対象と実効コストを args で送る（009 §12）。クライアントは確認ステップ（選ぶ → [Explore]、[Cancel]）を**クライアント状態**で行い、サーバーには確定時の `actExplore` だけを送る（U7）。山札の上の探査は、確定までカードを公開しない（Q-15）。
- 山札の上の探査には、025・026 の探査禁止を適用しない（001 §6-3-1、FAQ 7、Q-29）。007 のロック（他者は獲得できない）も山札の上には適用しない（Q-29）。
- 探査コストの補正（探査中効果）は、手番プレイヤーの準備場の表向き（横向きでない）のカードの効果を、その手番中だけ適用する（Q-25、002 No.17）。013 を探査時に使って除外すると、その手番の補正（-1）が加わる。
- **自動パス**: 探査できる対象が 0 のときは 43 に入らずにパスし、ログに出す。ただし 41 で探査時効果（011・013）が使えるプレイヤーは必ず 42 を経由する（使った結果で探査可能になりうるため。009 No.17「任意効果を使っても探査できない場合だけ自動パス」）。
- 探査後は 44 `AcquireDispatch` へ。カードは獲得エリアへ置かれ、獲得時効果を即時解決する（001 Q-17）。

### 7. zombie（離脱プレイヤー）の既定行動

方針（003 §4 の暫定案を具体化）: 失敗リスクを取らず、他プレイヤーに迷惑をかけない選択をする。ゲームを止めない（B9）。複数アクティブ状態では、zombie の行動の後に必ず `setPlayerNonMultiactive` で非ブロッキング状態にする。`$this->getCurrentPlayerId()` は使わず `$playerId` を使う。

### 8. ゲーム進行度（`updateGameProgression`）の計算式【提案】

終了条件はコスト 8 の探査山札の枯渇と未確認帯域の獲得で、ラウンド数は不定。進行度は「終了に近づく度合い」として、探査山札の消費で測る。

```text
pile8_0    = ゲーム開始時のコスト 8 の探査山札の枚数（列に公開した後）
pile8      = 現在のコスト 8 の探査山札の枚数
g8         = 1 - pile8 / pile8_0                       # 終了条件②に最も直接つながる
cards_0    = 全探査山札（4 種）の開始時の合計枚数（列に公開した後）
cards_now  = 全探査山札の現在の合計枚数
gAll       = 1 - cards_now / cards_0                   # 未確認帯域の獲得は予測できないため補助指標
progress   = floor(100 * max(g8, 0.8 * gAll))
progress   = min(progress, 99)                         # ゲーム終了時（60 の後）にフレームワークが 100 を扱う
```

- 呼び出し: `updateGameProgression: true` を `RoundStart`（10）と `ReturnRefill`（53）に付ける。ラウンド単位で十分で、探査手番ごとの更新は不要。
- 探査山札は減る一方（036 の入れ替えと 011 の追加は山札の枚数を変えるが、減る方向のみ）なので進行度は単調増加する。
- 係数 `0.8` と「最大値を取る」方式は、実プレイのラウンド数の統計が取れるまでは暫定。進行度は離脱時の ELO 計算に使われるため（B10）、極端に早く 99 に達しないことだけ確認する（未確定事項 No.10）。
