## 目的

MINIMUM JOURNEY の BGA 版で使う**カード画像のアセット設計**（原本の縮小・スプライト化。CI で生成する）と、**盤面レイアウトの設計方針**を決める。(A) は実装者がこの仕様書だけで生成スクリプトを書ける具体性、(B) は作者がレイアウト案を見て判断できる明確さを目標にする。承認後、別タスクでスプライト生成スクリプトと画面を実装する。

## スコープ

- 対象: (A) BGA の画像制約、原本の実測、縮小サイズ・形式・シート構成、生成スクリプトの仕様、カード上の日本語テキストの扱い。(B) 領域配置案（PC・モバイル、3 人・4 人）、各領域の表示仕様、操作の方針、bga-cards の対応表、アクセシビリティ、後続への申し送り。
- 対象外: スクリプト・画像・CSS・JS の作成（本タスクでは行わない。`data/` も変更しない）、状態遷移（006）、DB・通知の詳細（007）、カード効果の実装（008）、CI / 同期ワークフロー本体（004 / 005）、ゲームルール（001）、効果の英語テキストそのもの（方針のみ決め、文面は別途）。

### 1. BGA の画像制約と必須のメタ画像

#### 1.1 画像の制約

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| 1 ファイルの大きさ | **【確認】食い違いあり。** Img は「一般的な推奨は、画像ファイルは十数個以内、各 2 MB まで」（原文: "no more than dozen of image files, 2Mb max each"）。Checklist は「各画像は 4 MB を超えない」（"Each image should not exceed 4Mb"）。 | Img / Checklist |
| 画像の総量 | **【確認】** 15 MB を超えない。超える場合は圧縮する（「パレット形式（indexed palette）への再エンコードも効く」）。正当な理由があるときは alpha 申請時にその旨を書く。 | Checklist |
| スプライト | **【確認】** 複数の画像（カードなど）は CSS スプライトにまとめる（Checklist: "Multiple images (i.e. cards) are compressed in Sprite"）。**スプライトの寸法は 4096×4096 px を超えない**（Android の最大テクスチャが 4096 のため。超えると端末によっては一部が表示されない）。 | Img / Checklist |
| 形式 | **【確認】** webp を「できる限り使う」。透過が必要なものは webp か png、不透明な大きい画像（盤、カード）は jpg でもよい。「カードの角丸の透過は不要で CSS でできる」とも書かれている。gif（アニメーション。非推奨）と svg（アイコン・抽象的な画像向け）も使える形式に挙がっている。 | Img |
| 自動変換 | **【確認】** png / jpg はデプロイ時に webp へ**自動変換**され、ブラウザが webp を受け付ける場合は CDN が変換後を返す。変換は**非可逆**で、まれに問題になる。対策は「手元で webp を作って、それを使う」。 | Img |
| 先読み | **【確認】** `img/` 直下の画像は、ゲームを開いたときに**すべて**ブラウザに読み込まれる。`img/` のサブフォルダ内の画像は既定では先読みされない。`this.bga.images.dontPreloadImage(s)` でも個別に外せる。 | Img / GameJs |
| 高解像度 | **【確認】** ブラウザのズームで画像がぼやけないよう、表示サイズより高解像度の画像を用意し CSS の `background-size` で合わせる。 | Img / Checklist |
| ファイル名 | **【確認】** 空白と括弧を含めない。 | Img |
| `background-position` の単位 | **【確認】** `background-position` を % で書くなら `background-size` も % にする。px・em・% のいずれかに**統一**しないと、フレームワークの拡大縮小で小数ピクセルになったとき Safari で数 px ずれ、読めなくなることがある。 | CssPage |
| 反映 | **【確認】** FAQ には、`game_box.png`・`game_icon.png`・`publisher.png` の更新に「Reload game box image」操作が必要、との記述がある。ただし GMM の Migration 節は「`game_` で始まる画像ファイルは廃止済みで、変更しても反映されない」と書いており、FAQ の記述は旧方式のものと見られる（§1.2）。それ以外の画像は即時反映（キャッシュ消去が必要なことがある）。 | FAQ / GMM |

- **食い違いの扱い【提案】:** 小さい方の **1 ファイル 2 MB 以下**を設計上限とする（003 と同じ）。総量は **15 MB 以下**、目標は **6 MB 以下**（§3 の推奨案で約 4.5 MB【実測】）。
- ファイル数【提案】: 先読みされる `img/` 直下の画像は十数個以内。推奨案では**カード用 2 枚**＋アイコン用 1 枚（§4.5）＋手書きの UI 画像（数枚）に収める。
- 形式【確認】: Img は SVG も使える形式に挙げている（「SVG はアイコンや抽象的な画像に効率的。ただしアイコンには Font Awesome の利用も検討を」）。自動の WebP 変換の対象は PNG と JPG と書かれており、SVG は変換されない。

- **`box-rot.png` の判定【実測・提案】:** 2048×2048 px・約 3.6 MB・透過・斜めから見た立体の箱。(1) **種類は合う**: Box が求める「透明背景の 3D の箱」そのもの。平面の箱絵を別に用意する必要はない。(2) **そのままは使えない**: Box は **280×280 px の PNG**。2048 px は大きすぎるので**縮小**する。容量上限は箱には記載がないが、2 MB（Title・Publisher・Banner の上限）より大きいので、念のため縮小する。(3) **縮小の方法**: 箱の絵の外側の透明な余白を除くと約 1092×1680 px（縦長）で、280×280 の正方形に収めると箱は約 182×280 px になる（左右に透明な余白）。試作した 280×280 の PNG（余白を除いて中央に収めたもの）は約 155 KB（256 色パレット化で約 40 KB）で、箱の立体感・ロゴ・イラストは小さくても判別できた【実測】。(4) **1 点では足りない**: Box だけでは Icon・Title・Banner・Display が揃わない（上の表）。
- **縮小版の置き場所【提案】:** メタ画像は `img/` ではなく管理画面から登録する（上記）ので、`src/` には置かない。縮小版の PNG は、必要なら生成スクリプトの出力（`build/` 配下）として作るか、作者が管理画面へ直接アップロードする。原本の `data/box/` は変更しない。

#### 1.3 提供済みの素材（作者提供。2026-10-13）

作者がゲーム箱とアイコン一式を `data/box/`・`data/icons/` に格納した（作者回答 2026-10-13）。アイコンは当初 PNG のみだったが、続けて **SVG 35 点**（既存の PNG と同名の 34 点と `crew.svg`）が追加された（作者回答「icons/にsvgも格納しました」「crew.svgも格納しました」2026-10-13）。

| 3 | `03_1` | `03_2` | `03_3` | `03_4` |
| 4 | `56` | `57` | `58` | `rev` |

**drift シート（base、13 列×4 行）:** カード番号 N（4〜55）について、`n = N - 4`、`col = n % 13`、`row = floor(n / 13)`。例: 004 は (0, 0)、016 は (12, 0)、017 は (0, 1)、055 は (12, 3)。

**zoom の drift:** `n = N - 4` として、`n < 30` なら `drift_a`（`col = n % 6`、`row = floor(n / 6)`）、`n >= 30` なら `m = n - 30` として `drift_b`（`col = m % 6`、`row = floor(m / 6)`）。

- 生成スクリプトが `build/sprites/manifest.json`（リポジトリには入れない。CI の成果物として保存してよい）を出力する。形式:

- **実行時の参照方法**:
  - **案 M1（推奨）**: 並び順の**規則**（§4.2）を JS の小さな関数（スプライトキー → シート・列・行）として実装する。マニフェストは実行時には読まず、**CI で「マニフェストと JS の関数の結果が全 72 枚で一致すること」を検査**する（食い違うとビルド失敗）。画像を読む追加リクエストがなく、BGA の配信対象にも依存しない。
  - **案 M2**: マニフェストを JSON として配信して `fetch` する、または生成した JS ファイルを `src/` に出力して読み込む。`img/` や `modules/js/` への任意ファイルの配置・配信可否が**【未確認】**のため採らない。
  - 検査の実現方法（JS の関数を Node から import できる形に切り出せるか、`Game.js` 内の定数をどう検査するか）は、BGA が `modules/js/` に複数ファイルを置けるか【未確認】に依存する。実装タスクで決める。
- **CSS からの利用【提案】**: CSS は 1 ファイル（`minimumjourney.css`）に全部書く必要がある（CssPage: "ALL the CSS directives for your game must be included in this CSS file"）。そこで、シートごとの URL、列数、行数と、カードごとの列・行は **CSS カスタムプロパティ**で渡す。単位は px に統一し、% は使わない（§1.1、CssPage の警告）。

```css
/* 例（実装時に調整）。カード幅 --mj-w は領域ごとに設定する。高さは 419/300 の比で求める */
.mj-card-front {
  background-image: var(--mj-sheet-url);
  background-repeat: no-repeat;
  background-size: calc(var(--mj-w) * var(--mj-cols)) calc(var(--mj-w) * 419 / 300 * var(--mj-rows));
  background-position: calc(var(--mj-w) * var(--mj-col) * -1) calc(var(--mj-w) * 419 / 300 * var(--mj-row) * -1);
}
```

- JS は `setupFrontDiv` / `setupBackDiv` で `--mj-sheet-url`・`--mj-cols`・`--mj-rows`・`--mj-col`・`--mj-row` を要素に設定する（BgaCards の例は `style.backgroundPositionX` を直接設定しているが、カスタムプロパティでも同等）。
- フレームワークの自動縮小（CSS zoom）で幅が小数 px になる場合は、カード幅をなるべく整数 px にする（CssPage の対策の一つ）。zoom 階層の高さ比は 699/500 で、base とは別に計算する。

#### 4.4 rev の 716 px 幅、角丸・透過

- **rev の幅**: 全カードを `fit: 'fill'` で同一セルサイズ（300×419 / 500×699）に強制リサイズするので、原本の 715/716・998/999 のゆらぎは吸収される（§2）。rev だけ特別扱いしない。
- **角丸と透過**: 原本の角丸の透過（アルファ）を**そのまま残す**（WebP のアルファ付き）。CSS の `border-radius` を重ねて切り抜かない。選択枠などの輪郭だけは原本の半径（幅の約 4.2%）に合わせた `border-radius` を使う（`cardBorderRadius` に同値を渡す。§10）。【実測: 角の半径 約 30 px / 715 px】

#### 4.5 アイコンの生成物【提案】

提供済みのアイコン（§1.3）の扱い。作者が SVG を提供したため（No.20）、**入力は `data/icons/` の SVG を正とする**。PNG（`@4x`）は**使わない**。SVG のラスタライズに失敗する場合や、SVG の見た目に不具合があった場合のフォールバックとして `data/icons/` に残すだけにする。使う SVG は No.19 で確定した **18 点**（シンボル lv0〜lv4・lv6・ammulet の 7、数値・属性 power・fame・cost・flag の 4、乗組員 crew の 1、効果タイミングのラベル 6 種）。他の 17 点（event 系、lv5、matinanance、return、exploration、spaceship、ラベル 9 種）は使わない。`event.svg`（フォントに依存する `<text>` を含む）も対象外。

- **名前の対応:** 原本のファイル名に日本語・綴りの誤り（`ammulet`、`matinanance`）が含まれる。Img の制約（空白と括弧なし）は満たすが、CSS・JS から使う識別子としては不安定なので、**原本のファイル名 → ASCII の安定した名前**の対応表（スクリプト内の定数）を持ち、出力には ASCII の名前だけを使う。対応: `lv0` → `sym_earth`、`lv1` → `sym_solar`、`lv2` → `sym_galaxy`、`lv3` → `sym_virgo`、`lv4` → `sym_laniakea`、`lv6` → `sym_unknown`、`ammulet` → `charm`、`power` → `power`、`fame` → `fame`、`cost` → `cost`、`flag` → `flag`、`crew` → `crew`、`ドロー時` → `tm_draw`、`探査時` → `tm_explore`、`探査中` → `tm_exploring`、`探査力変動` → `tm_power_mod`、`名声変動` → `tm_fame_mod`、`獲得時` → `tm_acquire`。対応表に無いファイルが使用対象として指定されている、または対応表の原本が無いときは、入力検査（§5.2）と同様にエラーにする（使わないファイルが `data/icons/` にあるのは正常）。
- **BGA での SVG の扱い:** **【確認】** Img は SVG を使える形式に挙げ、「SVG はアイコンや抽象的な画像に効率的」と書く（https://en.doc.boardgamearena.com/Game_art:_img_directory 、最終更新 2026-06-29）。自動の WebP 変換は PNG と JPG だけが対象。**【未確認】** 本プロジェクトの `img/`（サブフォルダを含む）に置いた SVG が、実際に CDN から正しい種類（`image/svg+xml`）で配信され、CSS の `background-image` や `<img>` から表示できるか。Wiki に配信の詳細（サブフォルダ、Content-Type）の記載がなく、Studio で試していない（未確認事項 U12）。

**比較: SVG をそのまま置く案と、CI でラスタライズする案**

| 観点 | 案 S: SVG を `src/img/icons/` に置く（18 点） | 案 R: CI で 1 枚のスプライト（WebP）にラスタライズ（推奨） |
| --- | --- | --- |
| BGA で配信されるか | 形式として許可されている【確認】。配信・サブフォルダは【未確認】（U12） | WebP のカードスプライトと同じ方式。許可・配信とも確認済み【確認】 |
| 先読みと読み込み | `img/` 直下に 18 個置くと「十数個以内」（Img）を超える。サブフォルダに置くと先読みされず、初回にアイコンが遅れて出る。リクエストが 18 回 | `img/` 直下の 1 枚（先読み 1 個、リクエスト 1 回。約 30 KB【実測】） |
| ファイル名 | 日本語・綴りの誤りを ASCII にする必要がある。`data/` は編集できないので、**コピー時にリネーム**するスクリプトが要る（生成せずコミットするなら、リネームした SVG が `src/` の手書き資産になる） | 同じ対応表が要る（出力はスプライト 1 枚と、セル位置のマニフェスト） |
| ログ・ツールチップでのインライン表示 | CSS の `background-image` か `<img>` で、`<span class="mj-icon mj-icon-power">` のように書ける。**HTML に SVG を直接埋め込む（インライン SVG）のは避ける**: 各 SVG の `<style>` が同じクラス名（`.cls-1` など）で別の色を指定しているため、同じページに複数埋め込むと色が衝突する | 同じく `<span class="mj-icon ...">` で CSS スプライトとして表示できる。クラス名の衝突は起きない。位置の計算（セルの規則）が要る |
| 容量 | 18 点で約 50 KB 前後【推定。35 点の全体は約 107 KB。SVGO 等で圧縮可】 | 約 30 KB【実測。下の寸法のロスレス WebP の合計】 |
| 高 DPI（Retina、DPR 3） | 解像度に依存せず常に鮮明 | **表示サイズの 3 倍で書き出せば、DPR 3 まで鮮明**（下の出力寸法）。それ以上の拡大や、ブラウザのズームで 300% を超える場合は粗くなる |
| 描画の差・安全性 | ブラウザの描画に任される（SVG の `<style>` は `<img>` や背景では有効。フォントは使わないので問題なし） | CI で描画を確定させるので、ブラウザやフォントの差が出ない。Wiki にある「大きい画像の自動 PNG→WebP 変換の劣化」も避けられる（WebP を自作） |
| 実装の手間 | 小（コピーとリネーム） | 中（スプライト生成。カードの生成スクリプトに同居できる） |

- **推奨【提案】: 案 R（SVG を CI でラスタライズして 1 枚の WebP スプライトにする）。** 理由: (1) SVG の配信が**【未確認】**なので、確認済みの経路（WebP）を安全側の既定にする。(2) 先読みが 1 個で、アイコンの出遅れがない。(3) ログのインライン表示で SVG のクラス名の衝突を気にしなくてよい。(4) 出力寸法を表示サイズの 3 倍にすれば高 DPI でも鮮明。**ただし Studio で SVG の配信が確認できれば（U12）、案 S も選べる**（高 DPI に最も強く、実装も小さい）。その場合は、アイコンの入力は変えず（SVG が正）、出力の形だけを切り替える。実装タスクの最初に Studio で SVG を 1 点置いて確認し、結果を仕様書に反映する。
- **ラスタライズの出力寸法【提案】:** SVG の `viewBox` の 1 単位 = **5 px**（表示サイズの約 3 倍。シンボル・数値・乗組員は画面で高さ約 24 CSS px 以下、ラベルは高さ約 20 CSS px 以下で使う前提）。sharp の `density` は 360（`width`・`height` 属性が無い SVG は 1 単位 = 1 px × density / 72 になる。実装時に寸法を検査する）。**【実測】** この設定での各アイコンの寸法（横×縦 px）: `lv0` 68×68、`lv1` 70×42、`lv2` 66×66、`lv3` 90×69、`lv4` 71×68、`lv6` 77×77、`ammulet` 53×81、`power` 63×63、`fame` 74×75、`cost` 61×61、`flag` 79×76、`crew` 64×83、`ドロー時` 182×61、`探査時` 152×61、`探査中` 152×61、`探査力変動` 232×61、`名声変動` 195×61、`獲得時` 153×61。
- **スプライトの構成【提案】:** `src/img/icons.webp`（`img/` 直下）。上段: 記号 12 点を 96×88 px のセル 6 列×2 行（576×176）に、セルの中央へ貼る。下段: ラベル 6 点を 240×64 px のセル 2 列×3 行（480×192）に貼る。全体 576×368 px、**ロスレス WebP（アルファあり）で約 30 KB【実測。個別のロスレス WebP の合計 約 33 KB】**。セルの順序は §4.2 と同様に固定（名前の対応表の順）で、セルより大きい出力が出たら入力検査でエラー。表示時は CSS の `background-size` を px 指定で出力寸法の 1/3 にして使う（§1.1 の `background-position` の単位の注意。カードと同じ規則）。
- **フォールバック【提案】:** SVG の描画に失敗した（または見た目が崩れた）ものだけ、PNG（`@4x`）を `data/icons/` から使えるよう、対応表に任意の `fallbackPng` を持たせてもよい。通常は使わない。
- **コミット:** カードのスプライトと同様に、生成物（`icons.webp`）はコミットせず CI で生成する（§5.5）。案 S に切り替える場合は、リネームした SVG をコミットする `src/` の手書き資産にするか、生成物（コピー）にするかを、そのとき決める。原本は `data/icons/` のまま変更しない。

### 5. 生成スクリプトの仕様【提案】

#### 5.1 置き場所・ファイル・コマンド

| 項目 | 内容 |
| --- | --- |
| スクリプト | `scripts/build-sprites.mjs`（生成）、`scripts/check-sprites.mjs`（検査）、`scripts/lib/sprite-layout.mjs`（§4.2 の並び順の規則。両方から使う純関数） |
| 依存 | リポジトリ直下の `package.json`（T-004 の lint と共用する想定。`"type": "module"`）。`sharp` を**完全一致のバージョン**で固定（例 `"sharp": "0.35.5"`。`^` や `~` を付けない）。`package-lock.json` をコミットし、CI は `npm ci` |
| 実行コマンド | `npm run build:sprites`（生成。既定の出力先は `src/img/`）、`npm run check:sprites`（既存の出力の検査だけ。生成しない）。`build:sprites` は最後に同じ検査を実行する |
| オプション | `--out <dir>`（既定 `src/img`）、`--manifest <path>`（既定 `build/sprites/manifest.json`）、`--quality <n>`（既定 80）。通常の運用ではオプションを使わない |
| Node | **20.9 以上**（sharp 0.35.5 の `engines`。**【確認】** `npm view sharp@0.35.5 engines`）。CI は現行 LTS（22）を使う |

- **ネイティブ依存【確認】**: sharp は libvips を同梱した**ビルド済みバイナリ**を npm の `optionalDependencies`（`@img/sharp-linux-x64`、`@img/sharp-darwin-arm64` など）から取得するため、**コンパイラや別途の画像ツールのインストールは不要**。npm のパッケージ情報で、linux-x64 / linux-arm64 / darwin / win32 のパッケージがあることを確認した（`npm view sharp@0.35.5`、ライセンス Apache-2.0）。ローカル（macOS arm64）では `npm i sharp` だけで動作した【実測】。GitHub Actions の ubuntu ランナーで `npm ci` が成功することは**【未確認】**（実装時に確認。linux-x64 のパッケージが存在するので成功する見込み）。
- WebP の書き出し（`libwebp`）も sharp に内蔵されている。`cwebp` や ImageMagick は使わない。

#### 5.2 処理手順

1. **入力の検査**: `data/cards/` の `.png` が §4.1 の 72 個のスプライトキーと**過不足なく**一致すること（欠け・余りはエラー）。各画像が RGBA で、幅 715〜716、高さ 998〜999 の範囲内であること（範囲外はエラー。原本が差し替わったことに気づくため）。
2. **縮小**: キーの順（§4.2 の並び順）に、各画像を `sharp(file).resize(cellW, cellH, { fit: 'fill', kernel: 'lanczos3' })` で縮小する。
3. **合成**: シートの寸法の透明キャンバス（`channels: 4`、背景 `{r:0,g:0,b:0,alpha:0}`）に、`composite` でセルの位置（`col * cellW`、`row * cellH`）へ貼る。
4. **書き出し**: `webp({ quality: 80, effort: 6, alphaQuality: 100, smartSubsample: true })`。出力先のサブフォルダ（`zoom/`）は必要なら作成する。メタデータは書き出さない（sharp の既定）。
5. **マニフェスト出力**: §4.3 の JSON を書き出す（キーは 72 個すべて。キーの出力順は固定）。
6. **出力の検査**（§5.4）を実行し、失敗したら非ゼロで終了する。

- アイコン（§4.5）は、`data/icons/` の入力検査（対応表の 18 点がすべて **SVG** として存在し、`<script>`・`<image>`・外部参照・`<text>` を含まず、`viewBox` があること。PNG は読まない）の後、各 SVG を `sharp(file, { density: 360 })` で PNG の画素へ描画し、寸法がセルに収まることを確認してから、セルの位置へ貼ってロスレス WebP で `src/img/icons.webp` に書き出し、マニフェストに各アイコンのセル位置を記録する。カードと同じく決定性（§5.3）と出力検査（§5.4）の対象。
- 同じ縮小条件（base と zoom）で 2 回ずつ処理するため、「元画像の読み込み」は 1 回にまとめてキャッシュしてもよい（実装の最適化。仕様には影響しない）。

#### 5.3 決定性

- 同じ入力・同じ sharp のバージョン・同じ設定から、**同じバイト列**を出力する。実装は、(a) ファイルの処理順を固定する（ソートしたキー順）、(b) 乱数・時刻・環境依存の値を出力に入れない、(c) メタデータを書かない、(d) 設定値を固定する（品質などは既定をコードに埋め込み、オプションで変えたときはマニフェストに記録する）、の 4 点を守る。
- **【実測】** 同じ Mac で、base（品質 80）を 2 回生成して SHA-1 が一致した（漂流シート 28a1d0ff5a…。初期＋特殊シートは 5 列×4 行の試作版 820a9c13f1… で一致を確認、推奨の 4 列×5 行版は ca22c88230…）。
- **【未確認】** 別の OS・CPU（macOS arm64 と GitHub Actions の ubuntu x64）で同じバイト列になるか。libwebp の SIMD 実装の差で変わる可能性がある。ローカルで生成した画像と CI の画像が一致することは**要件にしない**（見た目は同等）。CI の中で「2 回生成して一致する」ことを検査して、**同じ環境内の決定性**だけを保証する（T-005 の差分転送の効率のため）。

#### 5.4 出力の検査（`check-sprites.mjs`）

| 検査 | 基準 | 違反時 |
| --- | --- | --- |
| ファイルの存在 | §4.1 の 5 枚と §4.5 の `icons.webp` がすべてある。余計な画像がない（SVG をコピーする案 S に切り替えた場合は、その SVG も対象に加える） | エラー |
| 寸法 | 各シートの幅・高さが 4096 以下。マニフェストの値と実寸が一致 | エラー |
| 1 ファイルの容量 | 2 MB 以下（食い違う 2 つの公式値の小さい方） | エラー |
| 総量 | `src/img/` 全体で 15 MB 以下。**目標の 6 MB を超えたら警告** | 15 MB 超はエラー、6 MB 超は警告 |
| ファイル名 | `^[A-Za-z0-9_]+\.webp$`（サブフォルダは `zoom/`）。空白・括弧なし | エラー |

### 7. 画面構成の方針

#### 7.1 前提

- ルールブックのゲーム場（RB p.1 3 人、p.4 4 人）の配置: **中央に探査場**（上に未確認帯域カード、下に「探査山札」と、各探査山札の右に表向きの「探査場の列」が 4 段）。手前に**自分のデッキ**（左に自分の山札、右に準備場。準備場は 1 枚ずつ下にずらして重ねる）と、その右に**お守り**。4 人のときは、相手 3 人が上・左・右に並ぶ（相手の準備場は山札と並べて置かれる）。

- 【未確認】 PC のゲーム領域の実幅（プレイヤーパネルや BGA の列の幅を除いた値）。実装時に Studio で測る。

### 9. 操作の方針

#### 9.1 ドロー／ストップの選択（準備フェイズ。同時・非公開）

- ステータスバー（BGA の標準）に、**[Draw]（青、primary）**と**[Stop]（赤、alert）**の 2 つのボタンを出す。色の意味は BGA の規約（青=進める、赤=停止。Guidelines C.3、**【確認】**）に合う。文字ラベルを必ず付ける（色だけに頼らない）。山札が 0 枚のときは [Draw] を無効（グレー）にして、理由をツールチップに出す（001 §5-1-2）。
- 選択は**非公開**。選択後、自分の画面では選択したボタンを「選択済み」の表示にし、**[Change]（変更）**操作を出す。他のプレイヤーにはパネルに**チェックマーク（選択済みかどうか）だけ**を出し、内容（ドローかストップか）は見せない。全員の選択がそろった時点で**確定**し、一斉にカードを引くアニメーションで開示する（001 §5-2）。
- **選択の変更（確定。作者回答「変更可能」2026-10-13、未確定事項 No.6）:** 押した後も、**全員が選び終わるまでは変更できる**。流れ（【提案】）: (1) [Draw] か [Stop] を押す → 選択済み表示になり、反対側のボタンと [Change] 相当の操作が残る（反対側を押せば選択が切り替わる）。(2) 他の誰かがまだ選んでいる間は何度でも変更できる。(3) 最後の 1 人が選んだ瞬間に全員の選択が確定し、開示に進む。確認ダイアログは出さない（BGA はゲーム中のポップアップを推奨しない。Guidelines A.4）。
- **エッジケース:** 最後の 1 人が選んだ瞬間に確定するため、その直前に選択を変更しようとしたプレイヤーの操作と競合しうる。どちらが先に届いたかの順序は**サーバー側で決める**（先に処理された方が有効。確定後に届いた変更はエラーにせず、確定済みの旨を通知して無視する）。クライアントは確定の通知を受けたら変更操作を無効にする。
- 049 時間停止装置（他プレイヤーの開示後に選ぶ）の持ち主の選択は、開示後の選択になるため変更可能の対象外で、**押した時点で確定**する（確定。作者回答「ok」2026-10-13、No.16）。
- BGA のマルチアクティブ状態で「選択後もアクティブのまま変更を受け付ける」実現方法は T-006 で決める（ここでは決めない。§12）。
- 時間切れ・離脱（zombie）は T-006（003 §4: 既定はストップ）。

#### 9.2 探査対象の選択（探査フェイズ。手番順）

- 手番の人の画面で、**探査できるカード**（コストが自分の探査出力以下で、禁止効果などを反映したもの。**判定はサーバーが行い**、選択可能なカードの一覧をクライアントに送る）を**選択可能スタイル**（枠線＋明るく）、探査できないカードを**非選択スタイル**（暗く）にする。色だけでなく、枠線の太さと「+」アイコンなどの形でも区別する。
- 対象は、探査場の列のカード、未確認帯域カード（コスト 10）、**各探査山札の上**（山札を直接クリック。必要な探査出力はその山札のコストと同じ。001 §6-3）。山札の上を探査すると、宣言した時点でそのカードを公開して獲得し、取り消せない（001 §6-3-1）。
- **探査の確定には確認ステップを入れる（確定。作者回答「確認を入れるようにしてください」2026-10-13、未確定事項 No.10。先の回答「確認不要」は撤回された）。** 探査できるカードか山札をクリックしても、その時点では確定せず、選択状態になる。ステータスバーの **[Explore]** で確定し、**[Cancel]** で選び直す。山札の上の探査も同じ（選んだ時点ではカードは非公開で、確定すると公開されて取り消せない。001 §6-3-1）。確認にポップアップのダイアログは使わない（§9.4）。
- 操作の流れ（【提案】）: カードか山札をクリックして選ぶ → ステータスバーの **[Explore]（青、primary）** で確定し、カードが自分の「獲得カード」へ飛ぶ（**[Cancel]** で選択を解除して選び直す。ポップアップは使わない）。ステータスバーには **[Pass]（白、secondary）**も表示する（探査はパスできる。001 §6-3-5）。探査できるカードがあるときは [Pass] ボタンを残す。[Pass] に確認を入れるかは作者の回答がなく、現在の記述のまま（確認なし）にしている。
- **自動パス（確定。作者回答「自動パス」2026-10-13、未確定事項 No.8）:** 探査できるカードが 1 枚もないときは**自動でパスする**（[Pass] を押させない）。自動パスしたことはログに出す（確定。作者回答「ok」2026-10-13、No.17）。「探査できるカードがない」の判定範囲は、**列・未確認帯域・山札の上のいずれも、任意効果を使っても探査できない場合だけ自動パス**（確定。No.17）。判定はサーバーが行う。
- 追加探査（012 牽引可能コンテナなど）は、同じ UI をもう一度出す。

#### 9.5 カード拡大表示

- **PC**: カードに**ホバー**すると、zoom シート（500×699）から切り出した大きなカード（CSS 幅 360）と**英語の効果テキスト**（§6）をツールチップで出す。ホバー開始から 300〜500 ms の遅延を入れて、マウスが通り過ぎただけでは出ないようにする。
- **モバイル（タッチ）**: ホバーが使えないので**長押し（500 ms）**で拡大表示を開く（ポインターイベントで実装。Mobile）。選択モードのときはタップが「選択」になるため、長押しは選択とは別操作にする。選択モード以外のカードは**タップでも拡大表示**を開く。拡大表示は、画面の空いた所をタップすると閉じる（Guidelines B.1「モバイルでは外をタップしたら閉じる」）。
- **必須情報はホバー専用にしない**（Mobile: Do not make required information available only through hover）。`:hover` を使うスタイルは `.notouch-device` を前置する（Mobile、**【確認】**）。
- bga-zoom（全体のズームボタン）は**使わない**（確定。作者回答「ok」2026-10-13、No.13）。ガイドラインはズームボタンを避け、レイアウトで解決することを求める（Guidelines A.5、**【確認】**）。ブラウザのズームやピンチに耐えるよう、画像は表示サイズより高解像度にする（§3）。

### 11. アクセシビリティ・その他

- **色だけに頼らない【確認】**（Guidelines E.1、E.2、D.1）: 選択可否は、枠の太さ・アイコン・暗さの組み合わせで示す。ボタンは文字ラベルを付ける。プレイヤーの色は名前を縁取りで見やすくし、ライト／ダークの両方の背景で確認する（C.3）。横向きカードは形（回転）と斜線、探査コスト・順番はすべて数字で出す。
- **タップ領域**: 操作できる要素は 32×32 px 以上、できれば 40〜44 px（Guidelines E.3）。モバイルのカード（約 64×89 px）は条件を満たすが、重ねた準備場でカード 1 枚の見える幅が小さくなりすぎないようにする（最小 32 px）。
- **ダークモード【確認】**（CssPage）: BGA の切り替えは `html` に付く `data-theme="dark"` で判定できる。`@media (prefers-color-scheme: dark)` は BGA の切り替えを無視するため使わない。カード画像は共通で、**背景・枠・プレースホルダー（空きスロット）・バッジ・ツールチップの色**を CSS カスタムプロパティにして、`html[data-theme="dark"]` で切り替える。**背景色を固定して文字色を指定しない**のが典型的な失敗（CssPage）なので、固定背景には `color` も指定する。
- **アニメーション【提案】**: bga-animations を使い、通常は 0.5 秒、最大 0.8 秒（Guidelines D.3、**【確認】**）。同じ種類の多数の移動はまとめる（帰還フェイズで全カードが山へ戻る動きは 1 つのまとまりにして、シャッフルのアニメーションを 1 回だけ出す）。ループやバウンドなどの装飾はしない。`bgaAnimationsActive()` が偽のとき（リプレイの高速再生、観戦時のジャンプなど）は即時に反映する。詳細は実装時。
- **観戦者・リプレイ【確認】**（CssPage、GameJs）: 観戦者がいるとき、フレームワークが外側の要素に `spectatorMode` クラスを付ける。非公開情報（本人にだけ見える公開エリア、自分のドロー／ストップの選択）は出さない。観戦者向けの表示【提案】: 「自分の領域」は無く、**全プレイヤーを席順で同じ（縮小）表示**にし、ドロー／ストップ・探査のボタンは出さない。リプレイ中も同様（`g_replayFrom`、`g_archive_mode`）。名声の合計は既定で非表示のため観戦者にも出さない。ゲームオプションで表示にした場合も観戦者には出さない（確定。No.15、作者回答「観戦者にも見せない」2026-10-14）。ゲーム終了時の最終得点の表示（BGA の標準で終了時は得点が出る。暫定: オプションに関わらず終了時は表示）は未確定事項 No.15 の残りで、暫定案のまま。
- **ログ【確認】**（Guidelines D.2）: 誰が何をしたかをログに出す。カード名はログ内でアイコン／名前＋小さな画像で示す（長い文にしない）。
- **テキストの縮約**: 英語のカード名は長い（例: Solar System Exploration Manual）ため、見出しは省略表示（`text-overflow`）にして、全文はツールチップに出す。
- **プレイヤーの識別**: 001 国旗の絵柄（ランダム割り当て）は、プレイヤーの目印には使わない（確定。作者回答「ok」2026-10-13、No.12。色が付かないため）。
